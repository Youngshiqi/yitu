# Yitu 智能物流平台 PRD

**版本**：1.2<br>
**日期**：2026-08-09  
**状态**：待评审  
**产品定位**：用于 AI Agent 应用开发岗位面试演示的、具备真实履约约束的智能物流平台。

## 1. 问题陈述

普通物流练习项目往往只有订单 CRUD 和一个可任意修改的状态字段，无法体现真实的跨区域履约、任务责任、网点交接、费用复核、异常处理与可审计性；普通“AI + 业务”项目又常常只是在 CRUD 页面旁添加聊天框，模型不能可靠参与业务。

Yitu 需要提供一套适合纯线上演示的简易快递系统：客户下单后，由始发地快递员揽收并送到始发网点；干线运输仅模拟节点流转；到达目标网点后，由收件地快递员派送或由客户自取，最终完成签收。在该业务主架上接入云端大模型、RAG 和受控工具调用，使客户能通过自然语言下单、查询物流、解释运费和处理异常，同时保证权限、金额、状态和 SLA 等关键结果仍由确定性业务逻辑控制。

## 2. 产品目标

1. 在线完整演示跨城市快递从下单到签收的闭环。
2. 支持上门揽收、网点自寄、送货上门和网点自取的四种组合。
3. 通过角色权限、数据范围和状态机体现真实业务约束。
4. 通过物流轨迹、费用明细、SLA、通知、异常和审计形成完整履约能力。
5. 提供能够多轮补全信息、调用业务工具、引用知识、请求人工确认的 AI Agent。
6. 展示 Agent 的评测、可观测性、越权防护和失败降级，而不只是聊天能力。

## 3. 非目标

- 不实现真实车辆、班次、路线规划、分拨、中转和干线调度。
- 不接入真实 GIS、GPS、电子围栏或全国行政区数据。
- 不接入真实打印机、扫码枪、短信、支付、地图或物流硬件。
- 不实现快递柜、驿站、便利店代收和加盟网点结算。
- 不实现货到付款、月结客户、复杂促销和通用规则引擎。
- 不允许 AI 独立判定赔付责任、承诺赔付金额或绕过状态机修改运单。

## 4. 用户与角色

系统保留 5 个权限角色，但可准备 7 个预置演示身份。

| 角色 | 职责 | 典型演示身份 |
|---|---|---|
| `CUSTOMER` | 下单、支付、查件、自取和发起诉求 | 客户 |
| `COURIER` | 承接揽收或派送任务 | 北京揽收员、上海派送员 |
| `STATION_OPERATOR` | 网点验收、入站、出站、到站和自取核验 | 北京始发网点人员、上海目标网点人员 |
| `OPERATIONS_ADMIN` | 运营配置、异常处理、任务转派和演示干线推进 | 运营管理员 |
| `SYSTEM_ADMIN` | 账号权限、系统参数、知识库和审计管理 | 系统管理员 |

“揽收员”和“派送员”不是不同角色，而是相同 `COURIER` 角色承担不同类型的任务；“始发网点人员”和“目标网点人员”也不是不同角色，而是通过所属网点限制数据范围。

权限校验同时包含：角色能力、所属网点或服务区域、任务类型、任务归属、资源所有权和运单当前状态。Vue 菜单和按钮控制仅用于改善体验，FastAPI 必须对每次操作重新校验。

## 5. 核心领域模型

- **运单 Shipment**：贯穿全程的客户委托，包含寄收件信息、服务方式、当前履约状态和承诺时间。
- **快递员任务 CourierTask**：独立的揽收任务或派送任务，可由不同城市的不同快递员承接。
- **网点 Station**：负责一个或多个预置行政区的收寄、交接、派送或自取服务。
- **物流轨迹 TrackingEvent**：业务动作形成的追加式事实记录，不允许覆盖或删除。
- **运输段 TransportLeg**：始发网点到目标网点的模拟干线段，记录开始、预计到达和实际到达。
- **报价 Quote**：基于当时规则生成的预估费用快照。
- **支付 Payment**：独立于物流轨迹的模拟支付、补款和退款流水。
- **SLA 实例 SLAInstance**：某个运单阶段的起算时间、截止时间、完成状态和规则版本。
- **异常工单 ExceptionCase**：与运单关联但拥有独立生命周期的异常处理记录。
- **通知 Notification**：面向用户的逻辑通知及其各渠道投递状态。
- **会话 Conversation**：AI 对话及可审计工具调用记录。
- **运单草稿 ShipmentDraft**：对话下单过程中逐步补全的结构化数据。
- **用户记忆 MemoryItem**：经过筛选或用户确认、可被检索和删除的长期偏好或语义事实。
- **知识文档 KnowledgeDocument**：原始 PDF、版本、生效时间、解析状态和发布状态。
- **知识块 KnowledgeChunk**：带章节路径、页码、区块坐标和向量的可引用知识片段。
- **操作授权 AgentActionGrant**：绑定用户、草稿快照和具体写动作的一次性短期授权。
- **自取凭证 PickupCredential**：用于网点自取核验的限时凭证，只保存取件码哈希和尝试状态。
- **签收凭证 ProofOfDelivery**：记录签收方式、签收人、核验方式和签收时间。

## 6. 服务方式与履约流程

### 6.1 服务方式

寄件方式：

- `DOOR_PICKUP`：快递员上门揽收。
- `STATION_DROPOFF`：客户到直营网点自寄。

收件方式：

- `HOME_DELIVERY`：目标网点生成派送任务，由快递员送货上门。
- `STATION_PICKUP`：包裹到站后生成取件码，由收件人到网点自取。

四种组合均需支持。网点自寄不生成揽收任务；网点自取不生成派送任务。

### 6.2 主履约流程

```text
客户创建运单
→ 确认报价并模拟支付
→ 上门揽收任务或等待客户到店自寄
→ 始发网点验收入站
→ 模拟干线运输
→ 目标网点确认到站
→ 派送任务或等待客户到店自取
→ 完成签收
```

建议的主状态包括：

- `PENDING_PAYMENT`
- `PENDING_PICKUP`
- `PICKUP_ASSIGNED`
- `WAITING_FOR_DROPOFF`
- `PICKED_UP`
- `AT_ORIGIN_STATION`
- `IN_LINEHAUL`
- `AT_DESTINATION_STATION`
- `DELIVERY_ASSIGNED`
- `OUT_FOR_DELIVERY`
- `WAITING_FOR_RECIPIENT_PICKUP`
- `DELIVERED`
- `CANCELLED`
- `RETURN_REQUESTED`
- `RETURN_APPROVED`
- `RETURNING`
- `RETURNED_TO_ORIGIN_STATION`
- `RETURN_COMPLETED`

异常不应全部压缩成一个运单状态。异常工单独立存在；只有疑似丢失、严重破损等会阻断履约的异常才暂停正常流转。

系统不提供通用“修改状态”接口，而提供接单、确认揽件、网点验收、干线发出、模拟到站、接派送任务、开始派送、自取核验和签收等业务动作。

### 6.3 取消、派送失败与退回

取消和退回是独立业务动作，不能通过管理员直接修改状态完成：

- 运单未支付时，客户可以直接取消，不产生退款。
- 已支付但尚未揽收或自寄验收时，客户可以取消，关闭未完成任务并生成模拟全额退款流水。
- 包裹已被揽收后不再允许普通取消；客户只能申请拦截，运营管理员根据包裹当前节点决定是否转入退回。
- 包裹进入干线后，第一版不支持中途改变目标网点；拦截请求记录为异常工单，到达下一可操作网点后再决定退回。
- 收件人拒收或两次派送失败后，可由运营人员选择重新派送、改为网点自取或发起退回。

退回状态流转为：

```text
RETURN_REQUESTED
→ RETURN_APPROVED
→ RETURNING
→ RETURNED_TO_ORIGIN_STATION
→ RETURN_COMPLETED
```

退回使用新的运输段和必要的快递员任务，但仍关联原运单，不创建一张伪造的新客户运单。每次重新派送创建新的派送任务，旧任务以失败原因关闭；新的任务生成独立 SLA，原 SLA 保留并标记未达成或按规则豁免。所有取消、拦截、重派和退回动作必须包含操作者、原因、前后状态及幂等键，并生成轨迹与审计记录。

异常解除后必须通过明确的 `resume_shipment` 动作恢复履约，记录恢复人、恢复原因和恢复目标阶段。模拟退款仅记录支付流水，不接入真实资金渠道。

## 7. 地址与网点匹配

本项目不依赖真实全国数据。客户地址采用省、市、区和详细地址的结构化录入，区县使用项目预置的行政区编码。系统预置北京、上海、广州和深圳，每个城市至少 2 个直营网点及服务区。

- 上门揽收：根据寄件地址的区县编码自动匹配始发网点。
- 网点自寄：列出寄件区县内可用网点，由客户主动选择。
- 送货上门：根据收件地址的区县编码匹配目标网点。
- 网点自取：由客户选择目标自提网点，详细收件地址可选，联系人和电话必填。
- 未匹配到网点时提示“该地区暂未开通服务”；运营管理员可以人工指派并留下审计原因。

## 8. 电子面单与线上扫码

下单成功后，后端生成唯一运单号。二维码编码公开查询 URL 或随机查询令牌，Code 128 条形码编码运单号；码中不直接包含姓名、电话和地址。

Vue 前端负责展示二维码、条形码和电子面单，并提供：

- 复制运单号；
- 模拟扫码；
- 手动输入运单号；
- 可选的浏览器摄像头扫码；
- 面单打印预览或下载。

扫码只是识别运单。后端根据操作者身份、网点、任务归属和当前状态返回允许的业务动作。USB 扫码枪可视为键盘输入，但不作为演示前提。

网点自取时生成 6 位一次性取件码，数据库仅保存 Argon2id 哈希、随机盐、有效期、失败次数和核销时间；哈希计算还必须加入只存在于服务端密钥管理中的 pepper，避免低熵取件码在数据库泄露后被离线穷举。取件码默认在包裹离开自取网点、成功核销或运单结束时失效；连续输错 5 次后锁定，由网点人员核验收件人信息并重新签发。通知记录可以展示演示取件码，但普通日志、AI 记忆和模型上下文不得保存取件码。

签收必须创建 `ProofOfDelivery`，记录本人签收、他人代收或网点自取，签收人脱敏姓名、核验方式、签收时间、操作人和网点。网点自取必须同时满足正确运单、正确网点、有效取件码和未签收状态；重复核销返回原成功结果，不重复生成轨迹或通知。

## 9. 计价与模拟支付

### 9.1 计价

计费重量取实际重量和体积重量的较大值：

```text
体积重量 = 长 × 宽 × 高 ÷ 体积系数
计费重量 = max(实际重量, 体积重量)
```

费用由首重费、续重费、上门揽收服务费、末端服务费、偏远地区附加费、保价费和优惠组成。金额统一以“分”为整数存储，不使用浮点数。

运营管理员维护带版本和生效时间的区域价格模板。报价保存规则版本、输入数据和费用明细快照，后续改价不得影响历史报价。

客户下单时得到预估价；揽收员或网点人员复核重量、尺寸后生成最终价。价格上涨时进入待补款状态，补款完成后才允许始发网点发运。第一版实现模拟支付和补差价，不实现真实支付与复杂退款。

### 9.2 规则实现决策

第一版不引入通用规则引擎。物流状态约束写在确定性领域状态机中；价格、SLA 时长和服务参数采用数据库配置与版本化策略模块。AI 可以解释规则，但不能计算最终金额或改变状态约束。

## 10. SLA 与 ETA

### 10.1 SLA 所有权

运营管理员维护结构化 SLA 规则，系统根据线路区域、服务方式、服务等级、营业时间和节假日配置计算截止时间。系统管理员管理权限和技术参数，不决定运营时效；快递员和 AI 均不能修改 SLA。

SLA 分为：

- 客户承诺时效：下单时生成 `promised_delivery_at` 并冻结。
- 内部阶段 SLA：揽收接单、上门揽收、始发入站、干线到达、目标网点处理、派送接单和首次派送分别生成 SLA 实例。

每个实例保存起算时间、截止时间、完成时间、暂停时长、规则版本和命中原因。补差价或等待客户确认地址等场景可按结构化规则暂停计时。

### 10.2 RAG 中的 SLA 文档

结构化规则负责确定性计算和超时判定，RAG 保存自然语言政策、例外说明和操作规范。AI 使用 RAG 解释为什么采用某个时效、为什么暂停、如何处理风险，但不能代替规则表判定是否违约。

管理端必须提供 SLA 规则管理、规则版本、规则命中详情、即将超时、已超时和 AI 风险解释页面，因此规则不能只存在于向量库。

### 10.3 ETA

- `promised_delivery_at`：下单时承诺的最晚送达时间，冻结不变。
- `estimated_delivery_at`：根据最新轨迹和各阶段剩余标准时长动态更新的预计送达时间。
- `delivered_at`：实际签收时间。

确定性 ETA 由当前阶段开始时间和剩余阶段时长计算；AI 可以基于网点积压、历史同线路耗时和当前延迟产生动态预测与原因，但必须与承诺时间分开展示。

## 11. 无 GIS 的物流轨迹展示

客户通过节点级时间线浏览轨迹，不展示虚假的实时 GPS。每条轨迹包含事件类型、公开描述、发生时间、所在网点、前后网点和内部操作信息。

干线阶段显示运输段卡片：始发网点、目标网点、已运行时间、预计段到达时间、剩余时间、进度和风险状态。可用纯 UI 节点连线表达北京到上海，无需地图。

物流轨迹由业务动作自动生成并只追加，不与支付流水、通知记录或异常处理日志混为一体。管理员人工补录必须写明原因，并产生新的纠正事件，不覆盖原事件。

## 12. 通知模块

通知由领域事件异步触发，首版渠道包括站内通知、SSE 在线推送和模拟短信；邮件为可选增强。典型事件包括运单创建、任务分配、到达目标网点、自提码生成、开始派送、费用调整、派送失败、完成签收和异常工单更新。

系统保存逻辑通知及每个渠道的投递记录，支持待发送、发送中、成功、失败和重试状态。使用运单、事件类型和接收人组成的幂等键，避免重复发送。

通知模板由系统管理员维护，模板变量来自后端白名单。AI 可以生成通知草稿，但涉及赔付、责任和敏感异常的通知必须由运营人员确认。

## 13. 异常模块

第一版支持揽收失败、地址错误、联系不上收件人、拒收、破损、重量不符、网点滞留、疑似丢失和等待补差价等异常。

异常来源包括：

1. 快递员或网点人员人工上报；
2. SLA 监测任务自动创建或升级；
3. 客户投诉形成；
4. AI 基于对话与轨迹提出建议，经用户或运营人员确认后创建。

异常工单按 `OPEN → ASSIGNED → PROCESSING → WAITING_FOR_CUSTOMER → RESOLVED → CLOSED` 流转，保存严重程度、发现人、责任处理人、处理时限、凭证、解决方案和审计记录。

地址错误可修改地址并重新匹配网点及计价；联系不上可重新派送或改为网点自取；重量不符触发复价和补款；严重破损或疑似丢失可暂停履约并升级运营管理员。所有处理动作仍需通过运单应用服务和状态机。

## 14. AI Agent 与 RAG

### 14.1 产品能力

Agent 面向已登录客户提供对话下单、查件、费用解释、规则咨询、异常解释和工单申请；面向运营管理员提供超时风险、网点积压、异常摘要和处理建议。

游客只能咨询公开规则，不能创建运单或查询个人数据。

### 14.2 对话下单

对话下单采用受控流程：

```text
自然语言需求
→ 提取结构化字段
→ 多轮追问缺失项
→ 更新运单草稿
→ 校验地址与服务范围
→ 检查禁限寄规则
→ 确定性计价
→ 展示完整确认卡片
→ 用户明确确认
→ 模拟支付并创建正式运单
```

会话记录、结构化草稿、缺失字段和待确认动作独立保存。地址、重量、尺寸或服务方式变化后，旧报价立即失效。

创建正式运单必须携带由后端生成的短期确认令牌；模型不能自行伪造用户确认。云端模型不可用时，普通表单下单仍然可用。

### 14.3 Agent 工具

首版受控工具包括：

- 获取当前客户资料和地址簿；
- 校验地址和匹配服务网点；
- 检查禁限寄物品；
- 创建或更新运单草稿；
- 获取确定性报价；
- 在用户确认后创建运单；
- 查询运单、物流轨迹、费用和 ETA；
- 检索物流知识；
- 在确认后创建异常工单或申请重新派送。

工具输入输出使用严格结构化模型。Agent 继承当前用户权限，不能查询其他客户数据；写操作必须经过业务校验和人工确认。

所有 Agent 工具必须调用与 Vue 页面相同的应用服务，不允许直接操作 ORM。每次调用统一执行：JWT 验证、资源所有权或网点范围、角色权限、领域状态机、参数校验、幂等键和审计记录。

敏感写操作在展示结构化确认卡片后，由后端签发 `AgentActionGrant`。授权必须绑定：

```text
user_id
conversation_id
action
resource_id 或 draft_id
draft_hash
quote_id 与 quote_version（涉及下单或费用时）
expires_at
nonce
```

授权默认 5 分钟有效、只能使用一次，并在数据库中原子消费。用户修改地址、物品、重量、服务方式或报价后，原授权立即失效。工具请求必须同时携带授权和幂等键；重复请求返回第一次执行结果，授权过期、参数哈希不一致、用户不一致或重复消费均拒绝并写入安全审计。

### 14.4 RAG 知识库

知识库包含禁限寄规则、包装规范、计费说明、保价赔付规则、自寄自取规则、派送失败 SOP、网点规范和 SLA 政策说明。文档具有标题、分类、版本、生效日期和来源。

检索流程采用问题改写、元数据过滤、向量与关键词混合检索、可选重排和引用回答。实时运单、费用和轨迹通过业务工具查询，不写入向量库。证据不足时 Agent 必须说明不确定并建议人工处理。

### 14.5 PDF 摄取与 MinerU 解析

系统管理员上传 PDF 后，系统异步完成安全校验、去重、解析、切片、向量化、人工预览和发布。上传阶段校验 MIME、PDF 文件头、文件大小和页数，使用 SHA-256 去重；原始文件必须保留，以支持重新解析和引用。

文档按以下状态流转：

```text
UPLOADED → QUEUED → PARSING → REVIEW_REQUIRED → PUBLISHED
                         └──→ PARSE_FAILED
```

只有 `PUBLISHED` 状态的文档可以参与线上检索。发布新版本时，旧版本进入 `ARCHIVED`；默认检索当前生效版本，回答历史运单问题时允许按业务规则版本检索历史文档。

MinerU 是 PDF 主解析器，运行在独立 Celery Worker 或解析容器中，不在 FastAPI 请求进程内执行。它负责中文 OCR、版面阅读顺序、标题、段落、表格、图片和区块位置提取；PyMuPDF 仅作为 MinerU 失败时的文本型 PDF 降级解析器。模型文件使用持久化卷，并限制单个任务的文件大小、页数、超时和并发数。

系统同时保存 MinerU 生成的 Markdown 和结构化内容，不将 Markdown 作为唯一解析结果。知识块必须保留：

- 文档 ID、版本和解析器版本；
- 标题与章节路径；
- 内容类型，包括段落、条款、表格或图片说明；
- 起止页码和区块坐标；
- 原始内容与向量；
- 生效日期和来源。

切片优先遵循标题、子标题、条款、自然段和表格边界。短条款和表格保持完整；过长章节再按约 500 至 800 个中文字符拆分并保留少量重叠。重复页眉页脚需要清理，但页码和引用坐标必须保留。表格转换为可检索的 Markdown，同时保存其章节和页码。

知识库管理页面提供原始 PDF、Markdown、章节树、表格、知识块、解析警告和页码引用预览。管理员确认解析质量后才可发布。Agent 引用应展示文档名、版本和页码；前端使用 PDF.js 打开原文并跳转到引用页，区块坐标完整时可进一步高亮。

价格和 SLA PDF 仅用于解释。最终金额、规则命中和截止时间仍以结构化业务数据为准。

### 14.6 云端模型

后端提供兼容工具调用和结构化输出的模型适配层，通过基础 URL、API Key 和模型名配置云端供应商。业务模块不直接依赖单一模型品牌。敏感字段不得进入普通应用日志。

### 14.7 Agent 安全与可观测性

- RAG 文档视为不可信资料，不能覆盖系统指令。
- 记录模型请求标识、耗时、令牌用量、检索片段、工具参数摘要、工具结果和错误。
- 对工具调用设置最大轮次、超时、重试和费用预算。
- AI 可做解释、预测和建议；金额、权限、状态、SLA 超时和正式业务写入由确定性代码裁决。

#### 14.7.1 云模型数据与隐私边界

发送到云模型的数据按以下等级控制：

| 等级 | 示例 | 云模型策略 |
|---|---|---|
| 公开 | 物流规则、公开网点名称 | 可以按需发送 |
| 业务内部 | 运单状态、费用明细、异常类型 | 只发送完成当前任务所需的最小字段 |
| 个人信息 | 姓名、电话、详细地址、对话内容 | 仅在已登录用户明确开启 AI 功能后按本次任务发送，并优先脱敏或占位 |
| 认证秘密 | 密码、JWT、API Key、取件码、确认令牌 | 永不发送 |

电话、已存在地址簿 ID 和运单号在模型上下文中优先替换为稳定占位符，由工具执行层还原；新地址自由文本仅在对话下单确有必要且用户已同意时发送。系统必须在 AI 页面说明云模型处理范围，并允许用户关闭 AI、删除会话和长期记忆；关闭后仍可使用普通表单与物流查询。

模型供应商必须支持 HTTPS，优先选择可关闭训练和配置低留存或零留存的 API。API Key 只保存在服务端密钥或环境变量中，不进入前端、数据库和日志。模型调用日志只保存请求 ID、模型、耗时、令牌、费用、工具名称和脱敏摘要；不默认保存完整提示词。开发和面试环境只能使用预置演示个人信息，不使用真实客户数据。

删除 AI 会话时，消息和关联语义记忆进入删除流程；法律或审计必须保留的工具执行记录应匿名化用户内容，仅保留动作、结果和追踪标识。所有模型调用使用 `trace_id` 关联 API、检索、工具和数据库审计。

### 14.8 AI 记忆

模型本身不作为可信记忆存储。系统将记忆分成四层：

1. **会话消息**：用户消息、Agent 回复、工具调用和令牌用量持久化到 PostgreSQL，用于恢复会话和审计。
2. **会话工作记忆**：当前意图、运单草稿、缺失字段和待确认动作持久化到 PostgreSQL；Redis 只缓存短期执行状态、流式响应和确认令牌。
3. **用户长期记忆**：默认寄件地址、常用联系人和明确偏好采用结构化字段保存。只有用户明确要求保存或确认的信息才能成为长期记忆。
4. **语义记忆**：不适合固定字段表示但有长期价值的信息保存为 `MemoryItem`，包含来源消息、类型、置信度、确认状态、有效期和向量。

每次模型调用按以下顺序组装上下文：

```text
系统指令
+ 当前用户身份和权限
+ 当前业务草稿
+ 最近若干轮消息
+ 历史会话摘要
+ 与当前问题相关的用户记忆
+ 本轮 RAG 检索结果
```

系统不把全部历史消息无限发送给模型；超出窗口的消息生成摘要，原始消息仍保留供审计。用户记忆、实时业务事实和公共知识严格区分：用户偏好来自记忆，运单与费用实时查询业务数据库，物流政策通过 RAG 检索。

长期记忆必须按 `user_id` 隔离，支持用户查看、更正和删除。支付口令、取件码、短期确认令牌及未经确认的模型推断不得写入长期记忆。电话和地址在界面及普通日志中脱敏，过期语义记忆由后台任务清理。

## 15. 前端范围

前端采用 Vue 3、TypeScript、Vite、Pinia、Vue Router 和 Element Plus。单系统内根据当前登录身份展示不同工作台；角色切换实质上是切换到预置演示账号并重新签发 JWT，而不是前端直接修改角色。

主要页面包括：

- 登录及演示身份选择；
- 客户表单下单、AI 对话下单、地址簿和通知中心；
- 运单详情、电子面单、费用明细、节点时间线、运输段和 ETA；
- 快递员揽收任务、派送任务、模拟扫码和异常上报；
- 网点入站、出站、到站、自寄验收和自取核验；
- 运营驾驶舱、任务转派、模拟干线、异常工单、价格规则和 SLA 监控；
- 系统用户、角色、网点、通知模板、知识库、模型配置和审计日志。
- 知识文档上传、MinerU 解析进度、原文与 Markdown 对照、章节/表格/切片预览和发布管理。
- AI 会话历史、用户可管理的长期记忆和隐私设置。

AI 对话下单采用左侧对话、右侧实时草稿与报价卡片的布局；关键字段和确认动作不能只存在于聊天文本中。

## 16. 通用架构决策

- 采用 FastAPI 模块化单体，按身份、运单、调度、网点、轨迹、计价、SLA、通知、异常、AI 和知识库划分模块。
- 使用 PostgreSQL 保存业务数据；RAG 使用 PostgreSQL `pgvector`，避免首版引入独立向量数据库。
- 使用事务性 Outbox 保存领域事件，后台任务负责通知投递、SLA 扫描和异步索引。
- Redis 用于后台任务、短期确认令牌和必要缓存；异步任务可采用 Celery。
- API 是核心业务入口，Vue 和 Agent 工具均调用相同应用服务，不复制业务规则。
- 操作日志、物流轨迹、支付流水、通知投递和 Agent 追踪分别建模，避免概念混用。

### 16.1 技术选型原则

技术选型按线上演示稳定性、Agent 工程深度、模块可测试性、招聘市场认知度和部署成本排序。首版不为展示名词而引入微服务、GIS、独立向量数据库或通用规则引擎。

### 16.2 固定技术栈

| 层次 | 技术 | 用途与决策 |
|---|---|---|
| 前端基础 | Vue 3、TypeScript、Vite | 单页应用与类型化开发 |
| 前端组件 | Element Plus、Pinia、Vue Router、Axios | 工作台、状态、路由与请求封装 |
| 可视化 | ECharts、Element Plus Timeline | 运营指标、SLA 和节点轨迹，不引入 GIS |
| 电子面单 | `qrcode.vue`、JsBarcode 兼容 Vue 组件 | 二维码和 Code 128 |
| PDF 预览 | PDF.js | 原文查看、页码跳转和后续区块高亮 |
| 后端 | Python 3.11、FastAPI、Pydantic v2 | API、校验及 Agent 工具结构化输入输出 |
| 数据访问 | SQLAlchemy 2、Alembic | 事务、并发控制与数据库迁移 |
| 主数据库 | PostgreSQL 16 | 业务事实、会话、全文检索和审计 |
| 向量检索 | pgvector | 知识块和经确认的语义记忆向量 |
| 缓存与队列 | Redis 7、Celery | 短期状态、通知、SLA 扫描、解析和索引任务 |
| Agent 编排 | LangGraph | 多轮状态、工具调用、中断恢复和人工确认 |
| 模型接入 | OpenAI-compatible 云端 API | 通过基础 URL、API Key 和模型名更换供应商 |
| PDF 解析 | MinerU 主解析、PyMuPDF 降级 | 中文 OCR、复杂版面、表格、页码和区块坐标 |
| RAG | PostgreSQL 全文检索 + pgvector | 关键词与向量混合检索，预留重排接口 |
| 实时消息 | SSE | Agent 流式响应与单向站内通知 |
| 认证 | JWT、Argon2 | 前后端分离认证和密码哈希 |
| 可观测性 | 结构化日志、OpenTelemetry，Langfuse 可选 | API、模型、检索和工具链路追踪 |
| 测试 | pytest、HTTPX、固定模型适配器 | API 旅程、领域规则和 Agent 评测 |
| 部署 | Docker Compose | 统一启动前端、API、Worker、PostgreSQL 和 Redis |

LangGraph 只编排 Agent 工作流，不替代物流领域状态机。PostgreSQL 是长期事实来源；Redis 不保存唯一业务状态；MinerU 在独立 Worker 中运行，避免占用 API 进程。

### 16.3 异步任务可靠性

业务事务与 Outbox 事件必须在同一个 PostgreSQL 事务中提交。Outbox Relay 使用事件 ID 作为消费幂等键，事件采用“至少一次”投递，因此通知、SLA 检测、文档解析和索引消费者都必须支持重复执行。

异步任务采用指数退避和随机抖动，默认最多自动重试 5 次。超过次数后进入死信状态，保存任务类型、业务 ID、最后错误、尝试次数和下次可操作建议。系统管理员可以在后台查看、修复原因并人工重放；重放沿用原业务幂等键，不能重复发送通知或重复写轨迹。

Worker 重启后从数据库任务状态恢复。文档新版本解析或索引失败时，旧的 `PUBLISHED` 版本继续服务；通知发送失败不回滚物流业务；SLA 扫描以阶段和时间窗口作为幂等范围，不能重复创建相同异常工单。管理端监控队列积压、任务失败率、最老待处理任务和死信数量。

### 16.4 中文混合检索与索引版本

首版不依赖额外 PostgreSQL 中文扩展。摄取时由 Python 应用层使用锁定版本的 `jieba` 生成空格分隔的 `search_tokens`，PostgreSQL 使用 `simple` 配置生成 `tsvector` 并建立 GIN 索引；向量检索使用 pgvector。系统归一化关键词相关度与向量余弦相似度后加权融合，并预留重排接口。

每个知识块保存分词器版本、Embedding 供应商、模型名、向量维度、切片策略版本和索引时间。更换 Embedding 模型或维度时创建新的索引版本并后台重建，完成质量检查后原子切换；不得在同一个向量列中混用不同模型生成的向量。检索必须同时过滤 `PUBLISHED`、生效时间、知识分类和适用角色。

### 16.5 可重复演示环境

系统提供确定性的演示种子数据：7 个演示身份、北京/上海/广州/深圳网点与服务区、价格和 SLA 规则、通知模板、知识文档，以及至少一条北京到上海的标准演示路线。

仅在 `APP_PROFILE=demo` 时启用演示登录、快速推进时间和重置能力；生产配置启动时必须拒绝注册这些路由。运营管理员可以创建新的演示场景，系统管理员可以通过二次确认执行一键重置。重置只清理带 `demo_tenant_id` 或 `is_demo=true` 标记的数据，不能按表无条件删除。

演示时钟通过统一 `Clock` 接口注入。快速推进干线和 SLA 只改变演示时钟或生成明确的模拟事件，不修改历史事件时间。预置“一键演示”脚本覆盖客户对话下单、模拟支付、揽收、始发入站、干线到站、派送和签收；重置后运单号、账号和场景入口保持可预测，确保多次演示结果一致。

## 17. 用户故事

1. 作为客户，我希望通过表单或 AI 对话创建运单，以便选择最方便的下单方式。
2. 作为客户，我希望 Agent 逐项询问缺失信息，以便不用理解复杂表单。
3. 作为客户，我希望在创建运单前看到结构化确认卡片和费用明细，以免 AI 误解我的需求。
4. 作为客户，我希望选择上门揽收或网点自寄，以适应不同寄件场景。
5. 作为客户，我希望选择送货上门或网点自取，以适应不同收件场景。
6. 作为客户，我希望系统根据区县匹配服务网点，以便知道订单是否可履约。
7. 作为客户，我希望查看电子面单、二维码和条形码，以便在线演示包裹标识。
8. 作为客户，我希望查看预估价、最终价和调价原因，以便理解费用变化。
9. 作为客户，我希望完成模拟支付和补差价，以便运单继续流转。
10. 作为客户，我希望按节点时间线查看物流轨迹，以便不依赖地图也能理解包裹位置。
11. 作为客户，我希望看到承诺时间和动态预计送达时间，以便区分服务承诺与实时预测。
12. 作为客户，我希望 Agent 解释运费、延误和下一步操作，并给出证据来源。
13. 作为客户，我希望收到到站、派送、补款、异常和签收通知。
14. 作为自取客户，我希望收到一次性取件码，并在网点核验后完成签收。

26. 作为运营管理员，我希望查看某个运单命中的规则版本和计算依据。
27. 作为运营管理员，我希望推进演示干线到站，而不需要真实运输系统。
28. 作为运营管理员，我希望查看即将超时和已经超时的运单并处理异常。
29. 作为运营管理员，我希望转派任务、处理异常和补录事件时留下原因与审计记录。
30. 作为运营管理员，我希望 Agent 汇总异常、引用 SOP 并建议处理动作。
31. 作为系统管理员，我希望管理账号、角色、网点、通知模板和知识文档。
32. 作为系统管理员，我希望查看模型、检索、工具调用和费用指标。
33. 作为系统管理员，我希望模型不可用时核心物流流程仍可运行。
34. 作为审核人员，我希望任何敏感写操作都有操作者、确认人、前后状态和原因记录。
35. 作为面试演示者，我希望快速切换预置身份并连续展示完整流程，同时保持后端真实权限校验。
36. 作为客户，我希望 Agent 记住经我确认的常用偏好，以便减少重复输入。
37. 作为客户，我希望查看、更正和删除 AI 保存的长期记忆，以便控制个人数据。
38. 作为客户，我希望 Agent 不把历史偏好误当成本次订单事实，以免创建错误运单。
39. 作为系统管理员，我希望上传中文 PDF 并异步查看 MinerU 解析进度，以便管理知识库。
40. 作为系统管理员，我希望预览原文、Markdown、章节、表格和切片后再发布，以免错误解析污染检索结果。
41. 作为系统管理员，我希望重新解析文档时保留原文件、解析器版本和历史发布版本，以便追溯结果。
42. 作为客户或运营人员，我希望 Agent 的 PDF 引用能跳转到对应文档页码，以便核实回答依据。
43. 作为客户，我希望在允许取消的阶段取消运单，并看到任务关闭和模拟退款结果。
44. 作为运营管理员，我希望处理拒收、派送失败和拦截请求，并通过可审计动作重新派送、改为自取或退回。
45. 作为网点人员，我希望通过限时取件码和签收凭证核验自取客户，避免重复核销和冒领。
46. 作为用户，我希望明确知道哪些数据会发送给云模型，并可以关闭 AI、删除会话和记忆。
47. 作为系统管理员，我希望查看失败异步任务、死信和队列积压，并能安全重放任务。
48. 作为面试演示者，我希望一键初始化、快速推进和重置预置流程，以便每次演示结果一致。

## 18. 测试决策

测试以外部可观察行为为主，不断言内部方法调用或 ORM 实现。

### 18.1 核心业务测试边界

以 FastAPI API 为最高层集成测试入口，覆盖四种服务组合从创建运单到签收的完整旅程，并重点验证：

- 非法状态跳转被拒绝；
- 错误角色、错误网点、非任务负责人和其他客户越权被拒绝；
- 两名快递员并发接同一任务时只有一人成功；
- 重复扫码、重复支付回调和重复 Outbox 消费保持幂等；
- 重量复核后报价快照、补款和发运限制正确；
- 业务动作、轨迹、通知事件、SLA 和审计记录保持一致；
- 自寄不生成揽收任务，自取不生成派送任务。

计价、状态机和营业时间 SLA 计算使用参数化单元测试覆盖边界值。通知和异步消费者以事件输入到可观察数据库结果为测试边界。

### 18.2 Agent 测试边界

以“对话输入 → 结构化草稿、工具调用、引用、审批或拒绝结果”为评测入口，使用固定模型响应或可替换模型适配器保证自动化测试稳定。准备至少 30 至 50 条评测样例，覆盖：

- 多轮字段补全和用户改口；
- 地址无法服务、禁限寄物品和报价失效；
- 正确选择结构化工具或 RAG；
- 不让模型自行计算价格或确认下单；
- 其他客户运单查询和越权工具调用拒绝；
- 提示词注入与恶意知识文档；
- 无证据回答、错误引用和模型超时降级；
- 异常工单、重新派送等写操作必须人工确认。
- 经确认的用户记忆能够召回，未确认推断、其他用户记忆和过期敏感信息不能召回；
- 长对话摘要后仍保留关键草稿字段，且原始消息可供审计。
- Agent 写工具在授权缺失、过期、已消费、用户不一致或草稿哈希变化时必须拒绝；
- 姓名、电话、地址等个人信息遵守云模型发送白名单，认证秘密在所有模型测试中均不得出现。

评测指标包括任务完成率、字段抽取准确率、工具选择准确率、引用命中率、越权拒绝率、幻觉率、平均耗时和单次会话成本。固定评测集的发布门槛为：

- 越权查询拒绝率和未确认敏感写操作拦截率必须为 100%；
- 工具选择准确率不低于 95%；
- 对话下单必填字段抽取准确率不低于 95%，端到端任务完成率不低于 90%；
- 有依据问题的引用正确率不低于 90%，无依据问题的拒答或转人工率不低于 95%；
- 计价结果由模型自行生成、授权重放成功和跨用户记忆召回的次数必须为 0；
- 使用固定模型响应的 CI 评测必须全部通过；云模型在线评测单独报告首个 SSE 事件 P95、完整响应 P95、令牌和费用，不因供应商瞬时波动阻塞核心业务 CI。

### 18.3 PDF 摄取测试边界

以“上传 PDF → 异步解析 → 管理员预览 → 发布 → 检索并引用”为集成测试入口，覆盖：

- 文本型、中文扫描型、多栏、表格和跨页内容；
- 重复文件、超限文件、损坏文件、解析超时和 Worker 重试；
- MinerU 失败后的 PyMuPDF 降级与明确质量警告；
- 标题路径、表格语义、页码和区块坐标保留；
- 未发布、已归档和错误版本文档不能参与默认检索；
- 新版本解析失败时不影响旧版本继续提供服务；
- PDF 中的提示词注入不能改变 Agent 系统指令；
- 引用页码能够打开正确原文页面。

### 18.4 业务恢复与演示测试边界

- 覆盖支付前取消、支付后揽收前取消、揽收后拦截、拒收、两次派送失败、重新派送、改为自取和退回完成；
- 验证旧任务关闭、新任务创建、SLA 重建、退款流水、轨迹和审计保持一致；
- 验证取件码错误、过期、锁定、重新签发、成功核销和重复核销；
- 模拟 Worker 在事件提交后宕机并恢复，验证 Outbox 不丢事件且消费者保持幂等；
- 验证 5 次失败后进入死信、人工重放和新文档解析失败时旧版本继续服务；
- 从空数据库执行演示种子和一键场景，完成全流程后重置并再次执行，结果必须一致；
- 中文关键词、同义表达和语义问题分别验证关键词、向量和混合召回，索引版本切换期间不得混用向量。

## 19. 验收标准

1. 演示者可以使用预置身份完成至少一条北京到上海的跨城运单全流程。
2. 四种寄收件组合均能完成，且任务生成符合服务方式。
3. 运单不能通过通用接口跳过必要状态，越权操作返回明确错误。
4. 电子面单、模拟扫码、费用、通知、轨迹、SLA、ETA 和异常均可在 Vue 页面查看。
5. 客户可以通过多轮 AI 对话生成草稿，经确认后创建正式运单。
6. Agent 能区分实时业务查询与知识检索，回答展示工具执行或文档引用。
7. Agent 不能越权查询、直接修改状态、独立确定价格或伪造用户确认。
8. 云端模型不可用时，表单下单、任务流转和普通查件仍可运行。
9. 管理端可以查看结构化价格/SLA 规则及历史版本，而不依赖 RAG 文档作为唯一事实来源。
10. 关键流程、并发、幂等、权限和 Agent 安全评测有自动化验证结果。
11. 用户可以管理自己的长期记忆，跨用户、未确认和敏感记忆不能被错误召回。
12. 管理员可以通过 MinerU 异步解析 PDF，预览结果后发布，Agent 回答能够引用文档版本和页码。
13. MinerU 解析失败不会阻塞 API 或破坏已发布知识，文本型 PDF 可以降级处理。
14. 取消、拦截、重派、改自取和退回均通过明确状态与任务流转完成，并产生正确支付、SLA、轨迹和审计记录。
15. 网点自取具备限时、限次、哈希存储和幂等核销，所有签收方式都有 `ProofOfDelivery`。
16. Agent 敏感写操作只能使用绑定当前用户和草稿快照的一次性授权执行，越权和重放拦截率为 100%。
17. 云模型请求遵守数据分级和最小发送原则，认证秘密不得离开服务端，用户可以关闭 AI 并删除会话和记忆。
18. 异步任务具备幂等、退避重试、死信、人工重放和服务重启恢复能力。
19. 演示环境可以一键初始化、推进和安全重置，连续两次执行得到一致的业务结果。
20. 中文混合检索具有可追溯的分词、Embedding 和索引版本，达到 Agent 评测发布门槛。

## 20. 已决问题与解决办法

| 问题 | 决策 |
|---|---|
| 揽收和派送是否由同一快递员完成？ | 否。分别生成揽收和派送任务，由不同地区快递员承接。 |
| 到站扫码的码从哪里来？ | 下单生成唯一运单号；Vue 展示二维码和 Code 128，码只包含查询 URL、令牌或运单号。 |
| 只能线上演示如何扫码？ | 支持模拟扫码、手动输入和可选摄像头扫码，不依赖硬件。 |
| 单系统切换角色如何保证权限？ | 切换预置演示账号并重新签发 JWT；后端执行角色、范围、归属和状态四层校验。 |
| 是否有管理员？ | 有运营管理员和系统管理员，共计 5 个权限角色。 |
| 为什么看起来有 7 个角色？ | 7 个是演示身份；揽收/派送由任务区分，始发/目标由所属网点区分。 |
| 没有真实地址数据如何分配网点？ | 使用预置区县编码和服务区域，自动匹配或由客户选择直营网点。 |
| 没有 GPS 如何生成轨迹？ | 每个业务动作生成追加式节点事件，客户通过时间线查看。 |
| 客户自寄和自取如何实现？ | 通过寄件方式和收件方式组合；自寄跳过揽收任务，自取跳过派送任务并使用一次性取件码。 |
| 运费如何计算？ | 使用版本化区域价格模板、计费重量、费用明细和复重补差价；金额以分存储。 |
| 是否使用规则引擎？ | 首版不使用通用规则引擎；确定性状态机加可配置、版本化的计价和 SLA 策略足够。 |
| 项目面向 AI Agent 岗位的亮点是什么？ | 对话下单、受控工具调用、RAG 引用、人工审批、权限继承、评测和可观测性。 |
| AI 如何对话下单？ | 模型补全结构化草稿，后端校验与报价，Vue 展示确认卡片，用户确认后才创建。 |
| 通知如何实现？ | 领域事件与事务性 Outbox 驱动站内通知、SSE 和模拟短信，支持幂等与重试。 |
| 异常如何实现？ | 独立异常工单生命周期，支持人工、SLA 和经确认的 AI 建议三类来源。 |
| SLA 截止时间由谁决定？ | 运营管理员配置规则，系统按版本计算并冻结实例，AI 只解释和预测。 |
| SLA 能否只写进 RAG 让 AI 判断？ | 不能作为唯一事实源；结构化规则供计算和管理，RAG 文档供自然语言解释。 |
| 不加入 GIS 如何浏览运输轨迹？ | 展示节点时间线和始发网点到目标网点的运输段卡片，不伪装实时位置。 |
| 不使用 GIS 如何判断到达时间？ | 通过阶段 SLA 和实时事件计算确定性 ETA，AI 可提供单独的动态风险预测。 |
| ETA 是什么？ | Estimated Time of Arrival，即预计到达或送达时间；与承诺时间和实际签收时间分开。 |
| AI 记忆保存在哪里？ | 会话、业务草稿和结构化偏好存 PostgreSQL，短期执行状态存 Redis，经确认的语义记忆使用 pgvector；模型本身不是记忆源。 |
| 整体技术选型如何决定？ | 以演示稳定、Agent 深度、可测试性、市场认知和部署成本为标准，采用 Vue 3、FastAPI、PostgreSQL/pgvector、Redis/Celery、LangGraph 和 Docker Compose。 |
| RAG 的 PDF 如何解析？ | 使用独立 Worker 异步执行 MinerU 主解析，保存 Markdown 与结构化区块；PyMuPDF 作为失败降级，发布前必须人工预览。 |
| Agent 如何安全执行下单等写操作？ | 使用绑定用户、动作、草稿哈希、报价版本、有效期和 nonce 的一次性 `AgentActionGrant`，并通过统一应用服务校验权限、状态和幂等。 |
| 云模型如何处理客户隐私？ | 按数据等级最小发送，认证秘密永不发送，个人信息需用户开启 AI 后按任务发送并优先占位；只使用服务端密钥和脱敏调用日志。 |
| 取消、拒收和退回如何闭环？ | 揽收前可取消，揽收后走拦截；拒收或多次派送失败可重派、改自取或进入独立退回状态链。 |
| 自取如何防冒领和重复签收？ | 取件码哈希存储、限时限次并支持锁定重签；核销生成签收凭证，重复请求幂等返回。 |
| 异步任务失败怎么办？ | Outbox 至少一次投递，消费者幂等，自动退避重试 5 次后进入死信，由管理员修复并安全重放。 |
| 如何保证面试演示可重复？ | 仅在 demo profile 启用预置种子、统一模拟时钟、一键全流程和按演示数据范围安全重置。 |
| 中文混合检索如何实现？ | Python 使用锁定版本的 `jieba` 生成检索词，PostgreSQL `simple` tsvector 与 pgvector 加权融合，分词、切片和 Embedding 全部版本化。 |
