# Yitu 完整后端优先设计

**状态：** 待用户书面审核

**日期：** 2026-08-09

**需求基线：** `docs/prd/yitu-smart-logistics-prd.md` 1.4

**开发规范：** 根目录 `.CLAUDE`

## 1. 目标与交付顺序

本设计将 Yitu 按“阶段化后端优先”方式实现。先完成 PRD 范围内的完整后端，集中清理并冻结 OpenAPI 契约，最后才开始 Vue 前端开发。

后端完成不是指一次性生成所有文件，而是六个可独立验收的阶段依次通过。每个阶段都必须具有可执行迁移、真实 HTTP 入口、自动化测试和可重复演示路径。

最终后端必须同时支持：

- 客户使用普通表单创建运单；
- 客户使用 AI 多轮对话补全草稿、确认报价并创建运单；
- 五种角色在真实后端权限约束下完成物流履约；
- 计价、支付、SLA、ETA、通知、异常、退回和审计闭环；
- 运营管理员或系统管理员通过管理 API 摄取和发布 RAG 文档；
- Agent 通过 RAG、查询工具和受控写工具完成业务协作；
- 云模型不可用时，全部非 AI 物流业务仍可运行。

## 2. 范围与非目标

### 2.1 后端范围

- 身份、认证、角色、资源范围和演示登录；
- 网点、服务区域、地址簿和确定性网点匹配；
- 运单、包裹、状态机、快递员任务、运输段、轨迹和签收凭证；
- 报价、复重、模拟支付、补款、退款流水和电子面单数据；
- SLA、ETA、通知、异常、重派、改自取、拦截、退回和审计；
- Outbox、Celery、重试、死信、人工重放和恢复；
- PDF 安全上传、MinerU/PyMuPDF 解析、预览、版本发布和混合检索；
- LangGraph 对话、工具、一次性授权、记忆、隐私控制、追踪和评测；
- 确定性演示数据、时钟、推进、重置和后端演示脚本；
- OpenAPI 契约、错误码、权限矩阵、示例和后端交付文档。

### 2.2 本轮不包含

- Vue 页面和前端状态管理；
- 真实支付、短信、地图、GPS、扫码硬件或物流设备；
- 微服务拆分、Kubernetes 和独立向量数据库；
- 真实车辆、线路优化、分拨和干线调度；
- 通用规则引擎或让模型替代确定性业务裁决。

## 3. 总体架构

采用 FastAPI 模块化单体、独立 Celery Worker、PostgreSQL/pgvector 和 Redis。

```text
HTTP / SSE
    │
    ▼
FastAPI 路由层
    │  认证、输入输出、OpenAPI
    ▼
应用服务层
    │  用例编排、权限、幂等、事务
    ▼
领域层
    │  状态机、计价、SLA、业务不变量
    ▼
SQLAlchemy 仓储与 PostgreSQL
    ├── 业务事实、审计、会话、Outbox
    └── tsvector + pgvector

Outbox Relay ──► Celery Worker ──► 通知、扫描、解析、索引
                         │
                         └── Redis 仅作队列与短期缓存
```

长期事实以 PostgreSQL 为准。Redis 不保存唯一业务状态。MinerU 不运行在 API 进程内。LangGraph 只编排 Agent，不替代物流状态机。

### 3.1 代码层次

每个业务模块遵循相同边界：

- `router`：HTTP、JWT 依赖、Pydantic 请求响应和状态码；
- `application/service`：组织一个完整用例和事务；
- `domain`：实体、值对象、状态转换和纯规则；
- `models/repository`：SQLAlchemy 持久化和查询；
- `tasks`：可重试的异步消费者；
- `schemas`：稳定的输入输出契约。

领域层不得依赖 FastAPI、Celery、模型供应商 SDK 或具体文件系统。Agent 工具不得直接访问 ORM。

### 3.2 模块职责

| 模块 | 核心职责 | 主要依赖 |
|---|---|---|
| `platform` | 配置、数据库、时钟、错误、幂等、审计、Outbox、追踪 | 无业务模块 |
| `identity` | 用户、角色、JWT、密码、演示身份 | `platform` |
| `stations` | 网点、服务区、地址匹配、地址簿 | `platform`, `identity` |
| `shipments` | 运单聚合、包裹、状态机、创建和查询 | `stations`, `pricing` |
| `dispatch` | 揽收/派送任务、接单、转派和并发控制 | `shipments`, `identity` |
| `tracking` | 客户轨迹、运输段、电子面单标识 | `shipments` |
| `pricing` | 规则版本、报价快照、复重和费用明细 | `stations` |
| `payments` | 模拟支付、补款和退款流水 | `pricing`, `shipments` |
| `sla` | 规则版本、实例、暂停、恢复、ETA 和扫描 | `shipments` |
| `notifications` | 模板、逻辑通知、渠道投递和 SSE | Outbox |
| `exceptions` | 异常、取消、拦截、重派、改自取和退回 | `shipments`, `dispatch`, `payments`, `sla` |
| `knowledge` | 文件、解析、版本、切片、索引、检索和引用 | Worker、pgvector |
| `agent` | 会话、LangGraph、工具、授权、记忆和评测 | 其他模块的应用服务 |
| `demo` | 种子、受控时钟、推进和范围化重置 | 全部业务模块 |

模块间通过应用服务和稳定 DTO 协作，不跨模块修改对方 ORM 实体。

## 4. 通用请求、事务与错误

### 4.1 普通业务请求

```text
路由接收请求
→ 验证 JWT、角色和结构化输入
→ 读取幂等键
→ 应用服务验证资源范围与当前状态
→ 领域逻辑计算转换结果
→ 同一事务写入聚合、轨迹、审计和 Outbox
→ 提交后返回稳定响应
```

所有改变状态的接口要求 `Idempotency-Key`。数据库保存请求指纹、执行状态和首次响应；相同键和相同请求返回首次结果，相同键但不同请求返回冲突。

### 4.2 统一错误

错误响应统一为：

```json
{
  "code": "INVALID_SHIPMENT_STATE",
  "message": "当前运单状态不允许执行此操作",
  "request_id": "01K...",
  "details": {}
}
```

- `code` 是稳定英文机器码；
- `message` 是简体中文可读说明；
- `request_id` 贯穿 API、Worker、Agent 和审计；
- `details` 只包含安全、结构化且不泄露内部实现的信息。

认证失败、权限不足、资源不存在、非法状态、幂等冲突、输入错误、外部依赖失败和内部错误分别映射稳定 HTTP 状态码。生产响应不得包含堆栈、SQL 或秘密。

### 4.3 时间、金额和隐私

- 业务时间统一为 `Asia/Shanghai`，API 使用带 `+08:00` 的 RFC 3339；
- 数据库时间点使用 `timestamptz`，所有当前时间来自可注入 `Clock`；
- 金额使用整数分，报价和规则均保存版本快照；
- 日志和客户轨迹对电话、地址、姓名等信息按规则脱敏；
- 密码、JWT、API Key、取件码和确认授权不得发送给模型。

## 5. 物流与商业履约设计

运单是客户委托的主聚合，一张运单在首版只对应一个实体包裹。快递员任务、运输段、支付、SLA、异常和通知具有独立生命周期，通过运单 ID 关联，不能压缩成运单上的任意字段。

所有状态变化都由命名业务动作触发，不提供通用状态修改接口。业务动作在同一事务中追加物流轨迹和审计记录。并发接单、取件码核销、支付回调和 Outbox 消费通过数据库条件更新、唯一约束和幂等记录防止重复执行。

四种寄收组合共享一条履约主链：

```text
创建与支付
→ 上门揽收任务 / 等待网点自寄
→ 始发网点入站
→ 模拟干线
→ 目标网点到站
→ 派送任务 / 等待客户自取
→ 签收凭证
```

报价、最终复价、补差价和退款都是独立流水。价格和 SLA 使用结构化、可版本化规则；RAG 文档只解释规则，不参与最终计算。

异常暂停履约时保留原事实。恢复、取消、拦截、重派、改自取和退回必须通过显式动作，创建相应的新任务、SLA、支付流水、轨迹和审计。

## 6. 异步任务与恢复

领域事务与 Outbox 事件一起提交。Relay 以事件 ID 投递 Celery；消费者按业务幂等键支持至少一次投递。

默认采用指数退避和随机抖动，最多自动重试 5 次。失败后进入数据库死信记录，而不是只留在队列中。系统管理员可以查看原因并安全重放。通知失败不回滚物流业务；知识文档新版本失败不影响旧发布版本；Worker 重启后从数据库状态恢复。

异步任务包括：

- 通知投递和 SSE 事件；
- SLA 扫描与异常升级；
- PDF 安全处理、解析、切片、Embedding 和索引；
- 长对话摘要、记忆过期清理和离线 Agent 评测；
- 演示环境中明确授权的批量初始化任务。

## 7. 文件与知识库设计

### 7.1 文件存储

本地演示环境使用持久化 Docker Volume 保存原始 PDF 和解析产物，并通过 `BlobStore` 接口访问。数据库只保存对象键、SHA-256、MIME、大小、页数和元数据，不把大文件直接存入数据库。该接口允许未来替换为 S3 兼容存储，但本项目不提前实现云对象存储。

上传接口使用流式读取和大小限制，校验扩展名、MIME、PDF 文件头、页数与哈希。文件名不能直接作为存储路径。损坏、加密、超限或不符合格式的文件在进入解析队列前拒绝。

### 7.2 权限

| 能力 | `OPERATIONS_ADMIN` | `SYSTEM_ADMIN` |
|---|---:|---:|
| 上传和查看解析进度 | 允许 | 允许 |
| 预览原文、Markdown、表格和切片 | 允许 | 允许 |
| 审核、发布、归档和停用 | 允许 | 允许 |
| 重新解析指定文档 | 允许 | 允许 |
| 修改解析器、Embedding、切片和索引配置 | 禁止 | 允许 |
| 查看或重放死信任务 | 禁止 | 允许 |

所有动作通过后端管理 API 完成，未来前端不得依赖开发者手工放置文件。

### 7.3 摄取与发布

```text
UPLOADED
→ QUEUED
→ PARSING
→ REVIEW_REQUIRED
→ PUBLISHED

PARSING → PARSE_FAILED
PUBLISHED → ARCHIVED
```

Worker 首先调用 MinerU；文本型 PDF 在 MinerU 失败时可用 PyMuPDF 降级，并标记质量警告。系统保留原文件、Markdown、结构化区块、表格、页码、坐标、解析器版本和历史发布版本。

人工审核后才发布。新版本发布采用原子切换；解析或索引失败时旧发布版本继续服务。只有 `PUBLISHED` 且在生效期内、适用于当前角色的知识块参与检索。

### 7.4 检索与引用

中文关键词由锁定版本的 `jieba` 生成 `search_tokens`，PostgreSQL `simple` tsvector 与 pgvector 分数归一化后加权融合，预留重排器接口。

每个知识块记录文档版本、章节路径、页码、坐标、切片版本、分词版本、Embedding 供应商、模型和维度。Agent 回答必须返回可追踪引用；证据不足时明确拒答或转人工。文档中的指令被视为不可信内容，不能改变系统指令或工具权限。

## 8. 两种下单入口

### 8.1 表单下单

```text
结构化表单
→ 校验地址、服务区、包裹与禁限寄规则
→ 生成确定性报价
→ 客户确认并模拟支付
→ ShipmentApplicationService.create
→ 正式运单
```

表单请求直接使用当前客户 JWT 和幂等键，不需要 Agent 授权。云模型不可用时该路径仍完整可用。

### 8.2 AI 对话下单

```text
用户自然语言
→ LangGraph 提取并补全 ShipmentDraft
→ 应用服务校验草稿
→ 确定性报价
→ 结构化确认卡片
→ 用户明确确认
→ 后端签发 AgentActionGrant
→ Agent 工具调用 ShipmentApplicationService.create
→ 正式运单
```

表单和 AI 入口共享地址匹配、禁限寄校验、计价、支付和正式运单创建服务。AI 不复制这些规则。AI 草稿可持久化、继续编辑并转换为普通表单；地址、物品、重量、尺寸、服务方式或报价改变后，旧报价与授权立即失效。

## 9. Agent 设计

### 9.1 图边界

LangGraph 保存可恢复的会话执行状态，典型节点为：

```text
接收消息
→ 加载身份、草稿、摘要和允许的记忆
→ 意图与风险分类
├── 普通回复
├── RAG 检索与引用
├── 只读业务工具
├── 更新草稿与缺失字段追问
└── 敏感写操作确认
       → 中断等待用户确认
       → 校验并消费 AgentActionGrant
       → 调用应用服务
→ 持久化消息、工具记录和追踪
```

图状态只保存编排信息，业务事实仍在对应业务模块。每个节点具有中文 docstring，解释输入、输出、路由条件和失败处理。

### 9.2 工具边界

- 查询工具继承当前用户和资源范围；
- RAG 工具只返回发布知识和结构化引用；
- 草稿工具只操作当前用户会话中的 `ShipmentDraft`；
- 敏感写工具要求一次性 `AgentActionGrant` 和幂等键；
- 所有工具调用与普通 API 复用相同应用服务；
- 工具层不直接操作 ORM，也不能自行计算金额或修改状态。

授权绑定用户、会话、动作、资源或草稿、草稿哈希、报价版本、有效期和 nonce。授权在数据库中原子消费；过期、重放、用户变化或请求指纹变化均拒绝并审计。

### 9.3 记忆与隐私

会话消息、工作草稿、结构化偏好和语义记忆分层保存。长期记忆只能来自用户明确要求或确认，按 `user_id` 隔离并支持查看、更正和删除。取件码、授权令牌、密码和模型推断不得成为长期记忆。

发送云模型前执行数据分级与最小化。认证秘密永不发送；个人信息仅在用户开启 AI 且本次任务必需时发送，并优先使用稳定占位符。关闭 AI 后，表单和普通业务接口保持可用。

### 9.4 模型适配与降级

业务代码依赖内部模型适配接口，通过 `base_url`、`api_key` 和 `model` 接入 OpenAI-compatible 供应商。供应商选择在 Agent 阶段开始前由用户确认，不写死品牌。

自动化测试使用固定模型适配器，不依赖真实网络。在线模型超时、限流或不可用时，保存可重试状态并返回明确降级说明，不能执行未经确认的写操作。

### 9.5 可理解性

AI Agent 是项目的重点学习模块。除中文关键注释外，每个 Agent 子模块交付时提供：

- 图状态和节点说明；
- 一条成功演示和至少一条失败/越权演示；
- 提示词、检索、工具、授权和确定性规则之间的边界说明；
- 对应测试入口与追踪字段说明。

## 10. API 契约策略

所有 API 使用 `/api/v1` 前缀。开发期间请求模型、响应模型、状态码、权限和错误码必须随代码维护，FastAPI 持续生成可用 OpenAPI；这不等于提前开发前端。

第六阶段集中完成：

- 接口命名、分页、筛选和排序一致性；
- 请求、响应、错误和幂等示例；
- 角色与资源范围矩阵；
- SSE 事件格式；
- 文件上传限制和异步状态说明；
- Agent 工具与普通 API 的关系说明；
- OpenAPI 快照与破坏性变更检查；
- 前端类型生成验证。

完成审核后冻结 v1。此后前端只依赖冻结契约；破坏性变化必须显式版本化。

## 11. 测试与质量门槛

### 11.1 测试层次

- 纯领域单元测试：状态机、计价、SLA、权限规则和授权哈希；
- PostgreSQL 集成测试：事务、迁移、唯一约束、并发和 pgvector；
- HTTP 旅程测试：以真实 FastAPI 接口完成角色流程；
- Worker 测试：Outbox、重试、死信、恢复、解析和索引；
- Agent 评测：固定模型响应、工具选择、引用、授权和隐私；
- 在线冒烟测试：仅在用户配置真实模型后运行，不阻塞普通 CI。

SQLite 不用于替代 PostgreSQL 行为测试。外部模型、短信和支付使用适配器与确定性假实现。

### 11.2 阶段完成定义

每个阶段必须同时满足：

1. 功能符合 PRD 和本设计；
2. 空数据库可执行全部迁移；
3. Ruff、mypy 和相关 pytest 通过；
4. 关键流程通过真实 HTTP 接口演示；
5. 权限、非法状态、幂等、并发和失败路径已覆盖；
6. 中文关键注释与阶段说明同步；
7. 不存在阻塞下一阶段的占位实现或未说明 TODO。

最终 Agent 门槛沿用 PRD：越权查询拒绝率和未确认敏感写操作拦截率为 100%，工具选择和字段抽取准确率不低于 95%，对话下单端到端完成率不低于 90%，有依据问题引用正确率不低于 90%。

## 12. 六个实施阶段

### 阶段 1：工程基础

交付 FastAPI、配置、PostgreSQL、Alembic、统一时间、错误、日志、认证骨架、幂等骨架、审计骨架、测试基础和 Docker Compose。退出时 API、数据库和测试闭环稳定运行。

### 阶段 2：物流核心

交付身份、网点、地址、运单、四种服务组合、快递员任务、模拟干线、轨迹、自取码和签收凭证。退出时所有角色可通过 HTTP 完成北京到上海的四种旅程。

### 阶段 3：商业与履约可靠性

## 14. 设计决策与延后决策

已经确定：

- 完整后端优先，API 冻结后再开发前端；
- 模块化单体，不提前拆微服务；
- PostgreSQL/pgvector 是长期事实与向量存储；
- Redis/Celery 处理短期状态和异步任务；
- RAG 文档由运营管理员或系统管理员通过管理 API 摄取；
- 表单下单和 AI 对话下单并存并复用同一应用服务；
- Agent 是核心展示与重点理解模块，关键注释使用中文；
- 需要用户执行 GUI、账户、密钥或付费操作时必须明确指导。

有意延后但不阻塞设计：

- 云模型供应商在阶段 5 开始前选择，代码先依赖 OpenAI-compatible 适配接口；
- Langfuse 是可选观测增强，基础追踪先保存在项目自身数据模型和结构化日志中；
- S3 兼容对象存储属于部署增强，本地演示使用 `BlobStore` 的 Docker Volume 实现；
- 重排模型属于检索增强，首版先实现可评测的关键词与向量加权融合。

这些延后项均有固定接口和触发时点，不属于未定义的占位需求。
