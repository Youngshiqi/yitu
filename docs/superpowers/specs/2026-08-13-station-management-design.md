# 运营管理员网点管理设计

## 目标

为运营管理员增加网点管理入口，支持网点查询、新增、编辑、停用、启用和安全删除，并在同一流程中维护网点覆盖区县及服务类型。

## 权限

- `OPERATIONS_ADMIN` 可以查看和管理全部网点及服务区。
- 其他角色只能继续使用现有的网点查询能力，不能修改网点。
- 所有新增、编辑、启停和删除接口都在后端再次校验角色。

## 数据模型

在 `stations` 增加：

- `enabled`：网点是否参与新业务，默认 `true`。
- `created_at`、`updated_at`：运营管理展示和审计所需时间。

网点所在地继续使用 `district_code`，但运营端不填写代码。前端选择省、市、区县区域 ID，后端校验区域层级并保存区县代码。

`service_areas` 继续保存“区县 + 服务类型 → 网点”的唯一映射。服务类型统一为：

- `HOME_PICKUP`：上门取件。
- `STATION_DROP_OFF`：网点寄件。
- `HOME_DELIVERY`：送货上门。
- `STATION_PICKUP`：网点自提。

同一个区县和服务类型只能属于一个网点。发生冲突时拒绝保存，返回原归属网点信息，不自动转移。

## 后端接口

- `GET /api/v1/admin/stations`：分页查询网点，可按名称、编码、状态筛选。
- `POST /api/v1/admin/stations`：新增网点及服务区配置。
- `GET /api/v1/admin/stations/{station_id}`：查询网点详情和服务区。
- `PATCH /api/v1/admin/stations/{station_id}`：修改名称、所在地和完整服务区配置。
- `POST /api/v1/admin/stations/{station_id}/enable`：启用网点。
- `POST /api/v1/admin/stations/{station_id}/disable`：停用网点。
- `DELETE /api/v1/admin/stations/{station_id}`：仅删除没有任何业务引用的网点。

现有 `GET /api/v1/stations` 默认只返回启用网点，避免客户选择停用网点。

## 保存规则

新增和编辑在单个数据库事务中完成：

1. 校验运营管理员权限。
2. 校验网点编码唯一。
3. 校验所在地为有效区县节点。
4. 校验每条服务区为有效区县节点。
5. 校验服务类型在允许集合内。
6. 检查“区县 + 服务类型”是否被其他网点占用；如有冲突则整次保存失败。
7. 写入网点和服务区配置。

编辑服务区采用完整替换语义：前端提交当前完整配置，后端在同一事务中计算新增、保留和移除项，避免多次请求产生中间状态。

## 删除与停用

- 网点被用户、运单、运输段、快递任务或其他历史业务记录引用时，不允许物理删除，返回 `STATION_IN_USE`，提示使用停用操作。
- 未被任何业务记录引用的新网点允许物理删除，并同时删除其服务区配置。
- 停用后，网点和服务区不参与新运单匹配及客户端网点选择。
- 历史运单和人员归属仍保留原网点引用。
- 启用前重新检查服务区冲突；若停用期间相关服务区已分配给其他网点，则拒绝启用并要求先调整配置。

## 运营端界面

运营工作区侧栏新增“网点管理”。页面包含：

- 网点总数、启用数、停用数和服务区数量。
- 分页列表：编码、名称、所在地、状态、服务区数量、更新时间。
- 新增和编辑抽屉：网点基本信息、所在地三级联动、服务区配置表。
- 服务区每行通过省、市、区县三级选择确定区域，并用多选框选择服务类型。
- 操作：编辑、停用、启用、删除。
- 删除和停用均需二次确认；服务区冲突展示冲突区县、服务类型及当前归属网点。

## 错误处理

使用稳定错误码：

- `STATION_CODE_CONFLICT`
- `SERVICE_AREA_CONFLICT`
- `STATION_IN_USE`
- `STATION_DISABLED`
- `INVALID_REGION_HIERARCHY`
- `REGION_DISABLED`

前端优先展示后端中文错误消息，不将冲突或引用错误统一显示为“保存失败”。

## 验证范围

按当前快速开发规则进行关键验证：数据库迁移、后端 Ruff/mypy、前端 TypeScript 检查，以及运营管理员通过 HTTP 完成新增、查询、编辑、停用、启用和无引用删除的完整流程。无需运行全量 pytest。
