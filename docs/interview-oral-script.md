# Yitu AI 物流助手：面试口述稿

> 这份稿子适合第一轮项目介绍，正常语速约 8 到 10 分钟。不要逐字背诵，记住每一段的主语、动作和设计原因即可。

## 1. 开场：先讲业务，不先讲技术

我做的是一个 AI 物流助手，核心场景是对话寄件。

传统寄件流程比较分散，用户需要在不同页面填写寄件地址、收件地址、物品、重量和尺寸，还要另外查询禁寄规则、计价规则和运单状态。我的目标不是单纯做一个聊天窗口，而是把这些物流操作收敛到一个统一的助手入口。

用户可以直接说“我想从北京寄一件衣服到上海”，助手会先理解他的意图。如果是查询本人运单，就读取他自己的数据；如果是问物流规则，就去知识库检索；如果是要寄件，就进入一个多轮寄件流程，逐步补齐字段，生成正式报价，等用户明确确认后再创建运单。

所以整个项目的核心闭环是：

```text
自然语言需求
 -> 识别任务类型
 -> 多轮补齐寄件信息
 -> 确定性校验和报价
 -> 用户确认
 -> 安全授权
 -> 创建运单
```

这里我有一个比较明确的工程原则：模型负责理解、选择工具和生成表达，但金额、权限、草稿版本、报价版本和建单，必须由确定性的后端服务负责。

## 2. 先给 Workflow 全貌

重构以后，我把 AI 执行真正放进了 LangGraph，而不是只在外面做一个路由。

整个系统有 15 个节点。主图有 7 个节点，负责统一助手入口；寄件子图有 8 个节点，负责寄件闭环。

主图的流程可以概括为：先加载上下文，再做安全检查，然后进入主 Agent。主 Agent 可以选择调用只读工具，也可以把请求交给寄件子图。流程结束后统一持久化回复；任何异常都进入显式失败节点。

主 Agent 和工具节点之间是一个受限的 ReAct 循环：

```text
assistant_agent_node <-> assistant_tools_node
```

寄件子图里面也有一个受限循环：

```text
draft_agent_node <-> draft_tools_node
```

这两个循环的含义是，模型可以根据工具结果自主决定下一步，但自主性是有边界的。工具是白名单，身份由后端注入，模型不能自己传用户 ID，也不能自己调用创建运单。循环还有限制，默认最多 8 轮 Agent 调用、4 次工具调用。

主图和子图使用两个独立的 State。主图 State 保存会话消息、待执行工具、寄件交接和最终结果；子图 State 保存草稿进度、缺失字段、报价、确认快照和工作流结果。两张图之间只交换 `ShipmentHandoff` 和 `ShipmentWorkflowResult`，避免把两个图的状态耦合在一起。

这里要特别区分两个概念：State 是节点之间传递的工作流数据，checkpoint 是 LangGraph 对 State、当前节点和 interrupt 位置的持久化。它们不是一回事。

## 3. 按一次对话寄件请求讲完整过程

现在我用一个实际例子说明：用户说“我要从公司地址寄一件衣服到上海”。

### 第一步：加载上下文和安全检查

请求进入 `load_context_node`。它根据会话 ID 和当前登录用户，读取最近 20 条对话消息，规范化成模型消息，然后把本轮用户输入追加进去。

这个节点不调用模型、不查 RAG，也不执行工具。它只负责准备短期上下文。

接下来进入 `security_gate_node`。这里用确定性规则检查提示词注入和跨用户运单访问。如果用户要求泄露系统提示词，或者查询别人的运单，就直接生成结构化错误，进入失败节点，不让请求继续触发模型。

### 第二步：主 Agent 决定走哪条路径

`assistant_agent_node` 会把系统提示词、历史消息和工具结果组装起来，调用支持工具调用的模型，并通过 LangGraph 的 stream writer 把模型增量 token 转成 SSE 事件。

主 Agent 可以选择几类工具：查询知识库、查询本人运单、读取地址、读取当前身份、读取计价规则，或者调用 `start_shipment` 把请求交给寄件子图。

如果用户只是问“我的快递到哪里了”，模型调用 `get_own_shipment`，工具节点执行后把观察结果放回消息，再回到主 Agent 生成答案。

如果用户说的是“我要寄件”，模型会调用 `start_shipment`。这个调用不是直接创建运单，而是生成一个 `ShipmentHandoff`，里面包括用户原话和模型提取出的候选字段，然后进入寄件子图。

### 第三步：寄件子图加载真实草稿

`load_draft_node` 会通过 `ShipmentWorkflowPort` 从数据库读取当前寄件草稿。草稿是业务事实，里面有已经填好的字段、草稿 revision 和仍然缺失的字段。

如果是第一次进入，就把主图传来的用户原话和候选字段放进子图消息里。这个节点不调用模型，主要作用是让后面的 Agent 基于最新数据库状态工作。

### 第四步：草稿 Agent 多轮补齐字段

`draft_agent_node` 会把当前已填字段、缺失字段和地址使用规则填入 `DRAFT_LOOP_PROMPT`，然后调用模型。它只有三个工具：`inspect_draft`、`update_draft` 和 `save_address`。

例如用户已经说了“寄一件衣服”，模型会调用 `update_draft` 更新包裹类别；如果地址不在地址簿里，就先追问收件人姓名、手机号、省市区和详细地址，信息齐全后调用 `save_address` 保存临时地址并回填草稿。

每次工具执行后，`draft_tools_node` 都会重新从数据库加载草稿，而不是只相信模型刚才的参数。这样可以避免模型继续使用过期状态。

如果模型没有工具调用但字段还缺失，子图返回 `NEEDS_INPUT`，把自然语言追问返回给用户。本轮图执行结束，下一轮用户补充信息时，再重新进入子图。

如果字段已经齐全，模型只需要表达“信息都齐了”，然后设置 `draft_ready`，接下来由确定性节点处理。

### 第五步：确定性校验和报价

`validate_draft_node` 会重新读取数据库草稿，确认字段是否真的完整。如果完整，进入 `create_quote_node`。

报价节点调用正式的 `DraftService.validate_and_quote` 和计价服务，生成报价快照。State 中会保存报价 ID、报价规则版本、草稿 revision 和金额。金额不是模型算出来的，而是后端业务服务算出来的。

### 第六步：人工确认

报价完成后，`request_confirmation_node` 会重新准备一份确认快照，包括寄件摘要、金额、草稿版本和报价版本，然后调用 LangGraph 的 `interrupt()`。

这时图会暂停，checkpoint 会保存当前工作流位置。接口通过 SSE 把“寄件内容和报价，请确认是否创建运单”发给用户。

用户下一次输入“确认”时，Runtime 会识别固定确认词，并用 `Command(resume=...)` 恢复图。如果用户输入“取消”，就返回取消结果；如果输入的是别的问题，就先暂缓当前确认，再把新问题作为新一轮请求处理。

这里模型不能替用户确认，确认词的解析是确定性的。

### 第七步：一次性授权和创建运单

用户确认后进入 `create_confirmed_shipment_node`。这个节点不会直接相信 checkpoint 里旧的状态，而是通过 Adapter 调用 `GrantService`。

授权 Grant 会绑定当前用户、创建运单动作、草稿 revision、报价版本、完整建单命令的 SHA-256 快照、随机 nonce 和 5 分钟过期时间。

消费授权时，系统使用数据库行锁检查授权是否属于当前用户、是否过期、是否已经消费、草稿或报价是否发生变化、快照是否被篡改。通过后才调用统一的运单创建服务，并使用幂等键防止重复创建。

所以这里有两层保护：LangGraph `interrupt()` 负责“暂停和恢复流程”，`AgentActionGrant` 负责“确认后的交易授权”。

## 4. RAG 怎么讲

我的 RAG 分为离线建库和在线检索两个阶段。

### 离线阶段

管理员上传物流规则文档后，系统先做格式、大小、哈希和安全校验，然后存入私有对象存储。

PDF 通过 Celery 异步提交 MinerU 解析，任务 ID 会持久化。Worker 重启后可以根据任务 ID 恢复轮询，不会重复提交。解析完成后取出 Markdown，保留标题、章节和页码信息。

接下来进行结构化分块。分块器会识别标题、章节路径、表格、条款和枚举项，超长内容才按句号或换行切分，并保留 overlap。每个 chunk 都保存标题、章节、内容类型和页码范围，这些信息以后会用于引用来源。

每个 chunk 建两类索引：一类是 Qwen 1024 维向量，存进 PostgreSQL 的 pgvector，并建立 HNSW cosine 索引；另一类是 Jieba 分词后的 PostgreSQL 全文检索索引，使用 `tsvector` 和 GIN。

索引是版本化的。在线检索只读最新版本、已经发布、并且处于有效期内的文档。

### 在线阶段

当主 Agent 选择 `search_knowledge` 时，查询进入 `KnowledgeRetriever`。

生产模型可用时，先进行一次查询改写，比如把“什么东西不能寄”改写成更适合检索的物流术语。改写超时或失败就用原查询，不阻塞主流程。

然后走两路召回：向量相似度召回和 PostgreSQL 关键词全文召回。两路候选合并后归一化，最终分数是：

```text
0.45 * 关键词分数 + 0.55 * 向量分数
```

如果配置了精排器，就把前 30 个候选交给模型按相关性打分；精排失败时保留原来的融合顺序。

检索结果不会直接变成答案，而是先包装成带文档名、章节、页码和正文的证据，通过工具观察结果回到主 Agent。主 Agent 再基于系统提示词和证据生成回答。

当前项目没有使用 MCP、GraphRAG 或 Elasticsearch。检索实现是 PostgreSQL 全文检索加 pgvector。当前是“证据约束生成”，还没有做到检索为空时完全在代码层切断模型调用，这一点我会如实说明。

## 5. 记忆怎么讲

我把记忆分成三层。

第一层是业务短期记忆，也就是 `agent_messages`。每轮用户和助手消息都会持久化，主图每次加载最近 20 条。

第二层是 LangGraph 工作记忆，也就是 checkpoint。它保存 State、节点位置和 interrupt，生产环境使用 PostgreSQL `AsyncPostgresSaver`，开发和测试可以使用 `MemorySaver`。它只负责恢复工作流，不是运单和报价的事实源。

第三层是长期记忆，保存在 `agent_memories`。它支持偏好、指令和个人资料三类记忆，创建需要用户明确确认，保存前会拒绝密钥、令牌和联系方式，并且可以设置过期时间。记忆可以生成向量，用 cosine 相似度召回；embedding 不可用时降级为按更新时间召回。

需要说明当前实现边界：长期记忆的存储、管理和召回服务已经存在，但新版 `load_context_node` 目前只加载对话历史，没有把长期记忆召回结果注入 Agent prompt。这个是后续可以继续完善的点。

## 6. 最后总结项目亮点

这个项目的重点不是“接入了一个大模型”，而是把大模型的自主性限制在可控范围内。

第一，LangGraph 不是装饰，而是真正负责主图、子图、工具循环、状态传递和 interrupt 恢复。

第二，寄件流程里，模型只负责理解和补齐草稿，报价、权限和建单全部走确定性业务服务。

第三，RAG 使用 PostgreSQL 全文检索和 pgvector 混合召回，支持文档版本、章节页码和可降级的查询改写与精排。

第四，敏感写操作使用 LangGraph interrupt 加一次性 Grant 双重保护，防止版本变化、重放、并发重复和快照篡改。

最后，这个项目当前实现的是通用物流助手、物流规则问答和对话寄件闭环，不包含物流异常自主处置。我认为这种边界清晰、能说明已实现和未实现能力的设计，比为了展示技术而堆叠 MCP、GraphRAG 或多 Agent 更适合生产，也更经得起面试追问。

## 7. 被打断时的短答

### 面试官问：这算 Agent 吗？

算受限领域 Agent。模型可以在两个 ReAct 循环里自主选择白名单工具，并根据工具结果继续决策，但不能越权、改金额或直接执行建单。

### 面试官问：为什么主图还要有子图？

主图负责统一入口和通用查询，子图负责寄件这个状态复杂、需要报价和人工确认的流程。两个图独立 State，通过 handoff 和 result DTO 交换最小信息，边界更清楚，也更容易测试。

### 面试官问：为什么不用 MCP？

当前工具都在同一个后端进程内，Port 和 Adapter 已经能提供类型约束、权限校验和事务边界。MCP 更适合跨进程或第三方工具生态，现在引入会增加复杂度。

### 面试官问：为什么 interrupt 后还要 Grant？

interrupt 解决的是工作流暂停和恢复，Grant 解决的是交易授权。Grant 会绑定草稿版本、报价版本和命令快照，并通过行锁、过期时间、一次消费和幂等键保护建单。

### 面试官问：长期记忆接入了吗？

长期记忆的表结构、API、敏感信息过滤和语义召回已经实现，但当前新版主图还没有把召回结果注入 Agent prompt。我会把它作为下一步接入点，而不会把已有子系统说成已经生效。
